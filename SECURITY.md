# Security Policy

## Supported versions

This repository currently publishes the `0.3.x` development line. Security fixes are evaluated against the latest supported release in that line. The v1.0 durability, approval, and evidence work described in the documentation is a development milestone, not a claim that a `1.0.0` release has been published.

## Reporting a vulnerability

Please do not open a public issue for a suspected vulnerability. Report privately through the repository owner's security contact or GitHub Security Advisories for this repository. Include the affected version, a minimal reproduction, impact, and any relevant logs with secrets removed.

Do not include API keys, tokens, private keys, credentials, personal data, or production information in a report.

## Scope and threat model

Stinky Cobbler is a local, read-only control plane. It intentionally rejects business-file writes, shell and test execution through the public Runtime, network and production access, secret/private-key reads, automatic Lease issuance, automatic approval, and automatic Task `DONE` transitions. `test-run` and `host-injected` remain unavailable public capabilities. Workspace-bound MCP tools fail closed unless the target has a regular, parseable `.stinky-cobbler/workspace.json`; a metadata directory alone is not a complete initialized workspace. This precondition is checked before Lease validation/reservation and capability execution, but it is not itself execution authorization. Beyond initialization, MCP also performs a full workspace-config schema and cross-reference admission in the same boundary (profile existence, profile-enabled packs, executable plugins, stable role IDs); an invalid config blocks with `WORKSPACE_CONFIG_INVALID` before any reservation or execution. Before the same admission steps, MCP also reads the persisted Audit outbox: `prepared` or `recovery-required` records, and any inability to read or validate pending state, block the invocation with `AUDIT_PERSISTENCE_FAILED`. Recovery remains explicit; a long-running process rechecks durable state at the next boundary and can clear only a stale in-memory degraded marker after no pending records remain.

The workspace metadata is local filesystem state. The workspace lock, durable JSON writes, and SHA-256 ledger chain help coordinate cooperative processes and detect some accidental or incomplete changes. Runtime admission is bound to the persisted workspace Task: the submitted task must already exist (created via `task create`) and exactly match its authoritative workspace copy, otherwise admission fails closed; this binding is a control-plane consistency check, not a signature, trusted time, or external attestation. Lock stale recovery is conservative: an owner is reclaimed only with validated metadata, a dead owner process, and an expired threshold; ownerless or malformed locks remain busy unless their lock-directory age is independently old enough for the limited local recovery rule. Callers must not invoke the same workspace lock concurrently from the same async context (sibling calls would bypass the serialization queue); no such call pattern exists today, and this is a documented constraint of the cooperative lock. The lock owner's `heartbeatAt` remains a static stale reference timestamp, not a periodic liveness heartbeat; RUNNING Agent Runs instead carry their own best-effort `heartbeatAt` (written at request boundaries, throttled to about 30s) that feeds stale-run recovery, so a freshly heartbeating run is not recovered. A run heartbeat is not proof of liveness, a distributed fence, a signature, trusted time, or external attestation. The lock does not provide a distributed lock, digital signature, actor authentication, trusted time, external witnessing, or protection against an attacker who can rewrite the workspace and recompute the chain. Leases are caller-supplied records (or user-confirmed issuances), not cryptographically signed credentials; the real boundary is the capability/writeSet allowlist, workspace containment, and policy denial — leases protect against misuse, not against forgery by a caller who already has the right to invoke the tools.

Receipt, Run, Audit, Ledger, and Evidence metadata are stored in multiple files and are not one database transaction. Approval records support an optional `expiresAt`; validity is evaluated at assessment time (preflight only matches unexpired approved records and `inspect` projects an `expired` flag) and never rewrites the stored status. The check is a local time constraint, not trusted time or external attestation. Runtime finalization treats a cancel/stale-recovery terminal Run as authoritative and will not overwrite it with an old owner result; it reuses an existing unique Run Receipt or records one aligned Receipt, while multiple/conflicting Receipts remain report-only. Runtime Evidence owner validation, idempotency, Evidence JSON creation, and the `evidence-recorded` Ledger append are serialized inside one workspace lock critical section, closing the stale-owner-before-write TOCTOU. This is not a multi-file transaction: Evidence that commits before a later cancel/recovery can remain orphaned and is report-only in diagnostics. The read-only `runtime diagnose` command reports cross-file lifecycle inconsistencies without creating locks or modifying control-plane files; an `INDETERMINATE` result means the available records are insufficient for a safe conclusion, not that the workspace is healthy or authorized. Broker-level unsupported/unauthorized requests return `RUNTIME_TOOL_NOT_ALLOWED`, ordinary tool/path/filesystem/read failures normalize to `RUNTIME_TOOL_FAILED`, and Evidence recording or validation failures, including a lost owner fence, normalize to `RUNTIME_EVIDENCE_PERSISTENCE_FAILED`; these outcomes fail closed. Evidence persistence stores metadata only; the current EvidenceRef hash covers the serialized tool-output envelope and is not proof of raw source bytes, a signature, or an external attestation.

## Release gate

Release candidates are verified but never automatically published. The `release-candidate` workflow requires a git tag that exactly equals `v${package.json.version}`, or — for `workflow_dispatch` — an explicitly declared version that matches `package.json`; `scripts/release-gate.mjs` enforces this as a pure consistency gate. CI and release workflows pin `actions/checkout`, `actions/setup-node`, and `actions/upload-artifact` to immutable commit SHAs (v4.4.0 / v4.4.0 / v4.6.2) rather than mutable tags, so the build steps cannot be silently redirected to different code. The workflow also generates a CycloneDX 1.5 dependency SBOM (`scripts/generate-sbom.mjs`, covering the full lockfile dependency tree with SHA-512 integrity hashes) and a SHA-256 checksum for the packed tarball (`scripts/generate-checksum.mjs`, sha256sum format), verifies both against the lockfile and the artifact, and uploads the tarball, checksum, and SBOM as a GitHub Actions artifact for independent download and verification. The SBOM is a dependency inventory with integrity hashes — it does not prove dependencies are vulnerability-free, that the build is reproducible, or that anything is signed. The checksum guards against transmission/copy corruption; it does not defend against an attacker who can rewrite both the artifact and the checksum, so anti-tamper protection still requires signing at publish time. Provenance and artifact signing are only performed at a real publish via `npm publish --provenance` (requiring OIDC/keys); this repository does not currently publish. The version gate, SHA pinning, SBOM, and checksum are not signatures or attestations; they ensure the release request declares the single version source of truth, the pinned steps run the reviewed action code, and the dependency tree and artifact contents can be independently checked.

## Response expectations

Reports are triaged privately. We will acknowledge a report when practical, reproduce it in a controlled environment, and document a fix or mitigation in the changelog when one is available. Please allow time for assessment before public disclosure.
