# 通用领域模型与扩展机制

## 核心定位

Stinky Cobbler 是通用 AI Agent 协作控制面，不预设“用户一定在开发代码”。

软件开发只是 `software-engineering` Pack；研究报告、内容创作、教育、运营、数据分析同样使用统一内核。

## 领域无关对象

| 对象 | 含义 |
|---|---|
| Principal | 个人、成员、管理员、审批人、外部参与者等主体 |
| Workspace | 数据、任务、策略与成员的隔离边界 |
| Task | 目标、输入、约束、预期产物、风险和任务状态 |
| Artifact | 文档、报告、数据、消息、设计、代码变更、媒体等产物 |
| Agent | 在独立上下文执行单一职责的角色 |
| Capability Lease | 短时、任务绑定、最小权限的能力授权 |
| Policy | 数据分类、用途、工具、外发、审批与保留规则 |
| Approval | 责任人对高影响行为的明确批准 |
| Audit Event | 可追溯的工具、产物、审批和副作用记录 |

## 通用任务状态机

```text
DRAFT
→ SCOPED
→ DESIGNED
→ APPROVED_FOR_EXECUTION
→ RUNNING
→ REVIEWING
→ VERIFYING
→ AWAITING_APPROVAL
→ ARCHIVED
→ DONE

任意阶段可进入：BLOCKED / REWORK / CANCELLED
```

`DONE` 仅代表：目标产物、验证证据、必要审阅和审批均满足当前策略；不代表 Agent 的建议永远正确。

## 产物优先模型

不同领域不共享代码仓库，但都共享产物治理。

```text
Artifact.type:
document | report | dataset | plan | design | message |
code-change | workflow-run | decision-record | media
```

每个产物至少记录：

```text
type、schema、version、provenance、sensitivity、status、review/approval state
```

代码 diff 是 `code-change`；研究结论是 `report`；客户邮件是 `message`；课程计划是 `plan`；视频素材说明是 `media`。

## 三层扩展机制

### Profile：谁在使用、默认如何交互

Profile 只定义默认体验与审批偏好，不定义底层工具权限。

```text
individual：个人，草稿优先，外发必须确认。
team：团队，任务可协作，默认保留审查和审计。
organization：组织，工作空间、成员、资料分级和审批链。
regulated：受监管组织，强制证据、白名单模型/插件、双人复核能力。
```

### Pack：某领域怎样做好工作

Pack 声明：

```text
任务分类
角色映射
产物 schema
质量规则
工作流模板
术语表
验证方式
策略叠加
推荐 Plugin
```

首批 Pack：

| Pack | 产物示例 | 专用角色扩展 |
|---|---|---|
| software-engineering | code-change、test-report、ADR | architect、builder、testwright、reliability |
| knowledge-work | research-report、meeting-note | researcher、fact-reviewer |
| business-operations | ticket、CRM update、quote draft | process-operator、communication-reviewer |
| creative-production | content-calendar、brand draft、media brief | creative-director、brand-reviewer |
| education | syllabus、quiz、learning-feedback | curriculum-designer、assessment-reviewer |
| data-analysis | dataset、notebook、dashboard、analysis-report | data-steward、analysis-reviewer |
| regulated-work | evidence-pack、risk-note | policy-guardian、human professional approver |

### Plugin / MCP：怎样连接具体能力

Plugin/MCP 只封装受控工具能力，不能绕过策略、审批、租约或审计。

```text
read_documents
query_crm
render_pdf
send_message
read_repository
run_tests
query_metrics
```

每个 Plugin 至少声明：输入/输出 schema、副作用等级、所需 scope、数据外发目的地、审计字段。

## 统一权限决策

权限不只看“能不能读代码”，而是：

```text
数据分类 + 行为 + 目的 + 去向 + 风险等级
```

| 等级 | 行为示例 | 默认处理 |
|---|---|---|
| L0 | 检索、总结、分析、草拟 | 可自动执行 |
| L1 | 内部草稿、标签、临时任务 | 可预授权，完整审计 |
| L2 | 更新 CRM、提交代码、改正式文档 | 显式授权或策略预授权 |
| L3 | 发邮件、公开发布、删除、签署、付款 | 人工确认；必要时双人审批 |

## 委派不扩权

```text
child_permissions ⊆ parent_permissions ∩ task_policy_permissions
```

任何 Agent 都不能通过创建子 Agent 获得自己本来没有的工具、数据或外发权限。

## 非代码任务的额外规则

- 外部文档、网页、邮件均视为不可信输入，不能修改系统策略或工具边界。
- 研究类产物必须标注来源、时效性和不确定性。
- 医疗、法律、投资等 Pack 默认是辅助分析，不是最终专业结论。
- 以组织名义发言、报价、发布、签署必须确认主体授权和审批记录。
- 临时 Agent 上下文、中间产物和外发数据都受 Workspace 数据分类和保留策略约束。
