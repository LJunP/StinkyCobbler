# v1.0 Durability Foundation 范围与安全边界

## 已实现

- Profile、Pack、Role、Plugin 与 JSON Schema 的本地加载和交叉校验；
- Task、Artifact、Lease、Receipt、Approval、Audit、EvidenceRef、TaskCapsule、AgentRun、ToolCallRecord 契约；
- `init` 与唯一 `.stinky-cobbler/workspace.json` 配置服务；
- CLI：`doctor`、`recommend`、`validate`、`config show/validate/doctor`、`init`、`task`、`receipt`、`runtime`、`runtime diagnose`、`audit`、`ledger verify`；
- stdio MCP 的契约、建议、Lease 检查与受 Lease 约束的本地只读仓库/Git/文档索引；受控调用在 Lease 校验前完成 workspace 初始化门禁与**完整 workspace config schema/cross-reference admission**（`WORKSPACE_NOT_INITIALIZED` / `WORKSPACE_CONFIG_INVALID` fail-closed）；
- 单次 `scripted-readonly` Runtime、Readonly Tool Broker、Evidence Ref、Run 存储与 Receipt；
- 最小 receipt/ledger 审计与 audit outbox 恢复；
- Plugin Manifest v2、确定性发现、重复 ID/operation 拒绝和逐项状态诊断；
- 静态受信任 Adapter registry；Runtime executor ID 不能是模块路径。

## v1.0 第一批：Durable Workspace Storage & Cross-process Consistency

控制面可变元数据的读改写经过 workspace-wide `.stinky-cobbler/workspace.lock`；JSON 临时写入、文件同步、rename 和目录同步提供崩溃后旧状态/新状态边界，ledger append 也会在返回前执行文件同步。Lease usage、Audit outbox、Task、Receipt、Run 和配置迁移共享该锁。锁的 stale-owner 处理只在能确认 owner 进程不存在且超过阈值时回收，无法证明 stale 时返回 `WORKSPACE_LOCK_BUSY`。缺失或损坏 owner 默认保持 busy，只有锁目录年龄满足保守的隔离回收规则时才尝试清理；lock owner 的 `heartbeatAt` 是静态 stale 参考时间，不是周期性心跳。**RUNNING Run 新增周期 `heartbeatAt`**：执行器在请求边界约每 30 秒写一次存活声明（wall-clock ISO，不产生 ledger 事件），stale 判定基准为 `heartbeatAt ?? startedAt ?? createdAt`，心跳新鲜时 `runtime recover` 拒绝；Run 心跳是尽力而为的存活声明，写入失败不影响请求执行，不是存活证明、分布式 fencing、签名、可信时间或外部见证。

这些机制不构成数据库事务、分布式锁、签名、身份认证、可信时间或外部见证。Receipt、outbox、Run 与 ledger 之间仍存在可识别的多文件崩溃窗口；Run 现在会以 `run-created`、`run-transitioned`、`run-recovered` 事件记录可观察的生命周期，并通过 `runId` 关联，但事件写入不与 Run JSON 构成事务。ledger 非法尾部默认只报告并等待显式 recovery，不自动截断、重写或宣称审计成功。Run 的 stale recovery 必须显式执行 `runtime recover`，只会把确认超过阈值且仍为 `RUNNING` 的 Run 标记为 `FAILED`/`RUNTIME_STALE_RECOVERY`，不创建成功 Receipt、不修改 Task、不推进 `DONE`。Runtime Run 可带 workspace-local `ownerToken`/`fenceEpoch`；cancel 或 stale recovery 后，旧执行路径在请求边界和最终状态写入时会被 cooperative fence 拒绝，但这不是身份认证、数字签名、硬中断或 distributed fencing。
## v1.0 第三批：Persistent Evidence References

成功的只读 Runtime Tool Call 会把 EvidenceRef metadata 写入 `.stinky-cobbler/evidence/`，并可通过 `evidence list/show/inspect` 查询。仅保存 ID、来源、locator、tool-output envelope hash、观测时间、敏感级别和 Tool Call 引用；不保存源文件正文或任意工具输出原文。当前 hash 不等于 raw bytes 证明、签名、可信时间或外部见证。

Evidence persistence 不启用 Evidence Gate，不改变 Approval preflight，不授权业务写入，不修改 Task 状态，也不推进 `DONE`。如果 metadata 或 ledger 持久化失败，Tool Call/Run 必须阻断并如实报告，不能留下声称成功但无法查询的引用。Evidence 与 Approval 是独立控制面边界。


Approval 记录现在可以在 `.stinky-cobbler/approvals/` 中显式请求、决定、查询和检查，并通过 `approval-requested`/`approval-decided` ledger 事件记录控制面变化。`approved` 只满足只读 preflight，不是 Lease、执行、业务写入或 `DONE` 授权；L3 仍被拒绝。Runtime、Receipt、Audit recovery 不会自动批准或创建 Approval。Approval 可带可选的 `expiresAt`：有效期在**评估时判定**（preflight 只匹配未过期记录，`inspect` 投影 `expired` 布尔），不自动改写存储中的 `status`，`expiresAt` 必须晚于 `requestedAt`，且只是本地时间约束、不是可信时间或外部见证。EvidenceRef 仍不是完整持久化证据库，Approval 与 Evidence 是独立边界。

只有绑定到受信任内置实现且状态为 `available` 的 Plugin 才标记为 executable；Pack 推荐不会自动启用 Plugin。

v0.3 不从 manifest、workspace config 或 CLI 参数加载任意模块，不下载依赖，不允许 Plugin 动态注册 MCP 工具。`scripted-readonly` 是唯一 available Runtime Adapter；`host-injected` 仍不可用。

## Runtime 的固定只读边界

```text
一个 workspace / task / agent / role / run
显式 Task Capsule + 显式 active L0 Lease
executor = scripted-readonly
allowed tools = repository-read, repository-list
writeSet = []
```

Runtime Admission 要求 Task 为 `SCOPED` 或 `DESIGNED`，且必须在 workspace 内持久化（`task create`）并与提交内容一致——缺失或与权威副本不一致时 fail-closed（`RUNTIME_TASK_NOT_PERSISTED` / `RUNTIME_TASK_AUTHORITY_MISMATCH`）；所有绑定一致，Role 不可写，Scope 不可包含控制面或敏感路径，预算与有效期合法。每个工具请求只能经 Broker 访问，保存 ToolCall、仅含 hash 与 locator 的 EvidenceRef 和 Receipt。

Runtime 绝不改变 Task state。`COMPLETED` 只表示 Run 生命周期结束，不表示验收、批准或 `DONE`。

## 统一入口 `/stinky-cobbler` 边界

- 路由由三层构成：命令文件（`.zcode/commands/stinky-cobbler.md`，安装到宿主目录）负责接收请求并给出执行规则；Skill（`.zcode/skills/stinky-cobbler/SKILL.md`）负责按 `via` 与 preflight 事实决策；CLI `entry preflight` 提供确定性的只读事实。不引入独立 router 进程。
- `via=skill` 不启动、不调用 MCP，不做本地读取；`via=mcp` 仅在 preflight 显示 MCP 已配置时经宿主 MCP client 调用 `stinky-cobbler-mcp`，未配置时明确报告并给出配置指引，不静默回退；`via=auto`（缺省）仅当请求需要读取本地文件、仓库或控制面状态时才走 MCP。
- `entry preflight` 只读：不创建 workspace、不获取 workspace lock、不写任何文件；非法 `via` 返回 `invalid-via` 且以非零退出码 fail-closed。
- `entry install-host` 必须由用户显式运行，包内没有 `postinstall`。它从不覆盖已存在的不同内容；写宿主 `config.json` 前在同目录备份原文件，且只合并新增的 `stinky-cobbler-local` server，不删除用户已有配置。dry-run 不产生任何写入。
- 用户最终看到的是“结果 / 证据 / 边界 / 下一步”的统一输出；`RUNTIME_RUN_FENCED`、ledger sequence、`EVIDENCE_*` 等内部错误码不以最终结论形式暴露（仅调试用户以 `--json` 查看）。

## 明确拒绝

- 任意业务写入、自动代码落盘、Git add/commit/push/PR、分支和 worktree；
- 任意 shell、测试执行器、网络/SaaS、消息、公开发布、部署与生产访问；
- `.env`、Secret、私钥、Token、restricted data 与控制面 Runtime 读取；
- 自动 Lease 签发、子 Lease delegation、自动审批、自动 `DONE`；
- 将计划、Receipt、Evidence、Run status 或账本链自洽解释为高风险授权。

Run/Ledger/Receipt 诊断只读取当前可验证文件，使用 ledger sequence 观察可见顺序，并将并发读取或损坏后的结论标记为 `UNVERIFIABLE`/`INDETERMINATE`。它不创建 workspace lock、不写入 Ledger、不补写生命周期事件、不删除或覆盖 Receipt，也不把 hash-chain 自洽解释为签名、可信时间、授权或历史真实性证明。


`ledger.jsonl` 是单 Node.js 进程内、按 workspace 串行追加的 SHA-256 前序 hash-chain。它可发现当前链中的 JSON、字段、顺序、前序链接或 hash 错误；不能提供数字签名、可信时间、外部锚定、不可篡改、主体身份或跨进程并发安全。v1.0 前仍需要这些硬化能力。
