# Stinky Cobbler 产品设计基线（终态）

> 状态：本文档为**已确认的设计基线**，记录用户确认过的产品决策与当前实现状态。后续所有批次以此为准，任何改动须回到本文档更新。最后更新：2026-08。

## 1. 产品定位

- 本地安装的 **AI 协作控制工具**：用户像引用 Skill 一样使用统一入口 `/stinky-cobbler`。
- 工具不是模型、聊天机器人或业务执行器；它调度受控的 AI 子 agent，管理权限、证据与审计。
- 安全优先：fail-closed、默认拒绝、一切可审计。

## 2. 最终形态（用户确认）

```text
用户输入 /stinky-cobbler <请求>
  → 用户唯一一次决策：via=skill 或 skill+mcp
  → Skill 评估任务（自动）：
      - 判断是否需要多个子 agent
      - 决定角色序列与执行方案
  → 常规任务：自动执行到底，不打扰用户
  → 关键决策（写入 / 高风险 / 方向性选择）：停下，展示选项，用户确认后继续
  → 返回统一结果
```

已确认原则：

1. **用户唯一决策** = 最开始选择 `via` 模式（skill 或 skill+mcp）。用户没有依据判断"是否用多个子 agent"，此判断完全由工具自动完成。
2. **调度自动**：是否多子 agent、角色序列、执行方案均由工具评估决定。
3. **确认分级**：常规任务（只读、低风险）自动执行；**关键决策**（写入、高风险、方向性选择）才要求用户确认。
4. **能力终态 = 分级能力**（见第 4 节）。

## 3. 授权模型

| 层 | 谁决定 | 何时 |
|---|---|---|
| via 模式 | 用户 | 每次请求开始（唯一用户决策） |
| 是否多 agent / 角色序列 | 工具自动 | 每次请求 |
| 常规执行 | 工具自动 | 只读、低风险 |
| 关键决策 | 用户确认 | 写入、高风险、方向性选择 |

- 关键决策的确认对象是**明确的清单**（如写入清单：文件 + 操作 + 用途），不是抽象描述。
- 确认动作持久化为 Approval 记录（扩展 `action` 类型），可审计。
- **确认载体 = AI 对话框点选式**（已确认）：Skill 在对话框内以标准选项格式弹出选择项（如 `[A] 全部确认 / [B] 部分确认 / [C] 拒绝`），宿主渲染为可点击选项；**用户点击选择，无需打字**；选择结果持久化为 Approval 记录后工具自动继续。宿主不支持渲染时退化为编号列表（点选或单字符选择）。

## 4. 分级能力（终态）

| 层级 | 能力 | 终态 |
|---|---|---|
| L0 | 只读（现状） | ✅ 保留，默认安全层 |
| **L1** | **受控写入**：用户确认 + writeSet 白名单 + 全审计 + 可回滚 | ⭐ 终态核心（规则见第 5 节） |
| L2/L3 | 外部动作（网络、消息、部署、发布） | ❌ 拒绝或极度受限 |

## 5. L1 受控写入规则（已确认，2026-08）

### 5.1 写入边界

```text
永远禁止（无论用户如何确认）：
  - .stinky-cobbler/ 控制面目录
  - 敏感路径（复用现有敏感名单：.env、credentials、密钥、.npmrc、token、netrc、keyring、*.tfstate 等）
  - .git/ 目录
  - 可执行文件 / 二进制（防注入）
  - 超过大小限制的文件（默认 1MB，可配置）

允许写入（白名单内）：
  - 写入清单明确列出的文件 + 用途
  - 清单由计划生成器根据用户请求产生
  - 必须经用户确认
```

### 5.2 写入确认流程

```text
子 agent 请求写入 → 生成写入清单：
  [
    { target: "docs/guide.md",     action: "modify", purpose: "修正拼写错误" },
    { target: "reports/summary.md", action: "create", purpose: "生成分析报告" }
  ]
→ 展示给用户（文件 + 操作 + 用途，不展示内容）
→ 用户：全部确认 / 部分确认 / 拒绝
→ 只执行被确认的写入
```

### 5.3 审计与回滚

```text
写前：原文件备份到 .stinky-cobbler/backups/write-<id>/（控制面内，可恢复）
写中：每次写入产生 Evidence（hash + 目标 + 用途）+ WriteIntent 记录 + ledger 事件
写后：Receipt 记录"写了哪些文件、基于哪个确认"
可追溯：任何时候能回答"谁、何时、经谁批准、写了什么、原文在哪"
备份保留：默认 30 天或用户清理（只在控制面内）
```

### 5.4 与调度计划的关系

```text
计划步骤的 writes 数组 = 计划生成器的"写入意图草案"
→ 用户确认后 = 批准写入清单
→ 子 agent 执行时只能写清单内文件
→ 超出清单的写入请求 → 拒绝并报告
```

## 6.1 调度规模上限（已确认，2026-08）

```text
步骤数（子 agent 调用序列）≤ 10
并行子 agent ≤ 4
单计划写入文件 ≤ 20
单请求限单个 workspace（不支持跨 workspace 调度）
```

## 7. 架构形态（已确认）

- **不引入独立常驻 daemon**。
- MCP server 在宿主会话内常驻（stdio）；调度由**宿主会话驱动**逐步执行。
- 所有状态（计划、步骤、子 Run）持久化在 workspace，进程崩溃后从持久化状态恢复。
- 多子 agent 通过 workspace 锁 + ledger + 持久化协调（现有机制）。

```text
宿主 AI 会话（常驻）
  → MCP 工具：生成计划（一步）
  → MCP 工具：执行步骤 s1（一步）
  → MCP 工具：执行步骤 s2（一步）
  → 计划状态持久化，进程死了也能恢复
```
