# Stinky Cobbler 使用说明书

> **定位**：Codex / ZCode 本地仓库的可验证权限与变更门禁。
>
> **版本事实**：本文描述当前实现边界。公开 npm 版本、GitHub tag/Release/资产和真实 Codex/ZCode 验证状态会变化，必须分别实时核验；源码版本、历史记录或 `mcpConfigured=true` 不能替代这些证据。
>
> 当前 checkout 只能视为源码候选；同一候选 bytes 的 Codex/ZCode 安装、重启、MCP 消费者和受控操作 E2E 在实际完成前均为 **UNKNOWN / PENDING**。

## 先理解边界

Stinky Cobbler 是本地 CLI/MCP 控制面。宿主负责实际推理和执行；本工具只对经自身受控通道的操作校验 TaskAuthority、精确 Approval、持久化 Lease、路径、单目标 WriteIntent 与写前 preimage，并记录 Evidence/ledger。

它不是：

- 自动 Agent 调度器或模型；
- 操作系统沙箱；
- 零配置产品；
- “所有数据绝对留在本机”的证明；
- 失败隔离或独立 reviewer 的宿主级保证；
- CAS 或长期 Context/Memory 系统。

Cooperative Mode 允许宿主原生文件工具、Shell、Git 和第三方 MCP 绕过控制面。若要强制中介，安装者必须另行隔离 worker 并只暴露受控工具；当前仓库未提供或验证该隔离。

## 安装与验证

安装公开版本前先查看 registry 实际版本：

```bash
npm view stinky-cobbler version --registry=https://registry.npmjs.org
npm install -g stinky-cobbler --registry=https://registry.npmjs.org
stinky-cobbler --version
stinky-cobbler doctor --json
```

验证当前 checkout 时从当前源码安装：

```bash
node --version                    # >= 22
npm install
npm run build
npm install -g .
stinky-cobbler --version          # 应与 package.json 一致
stinky-cobbler doctor --json
```

只有 GitHub Releases 实际存在对应 tag、checksum/SBOM 和附件后，才能把该版本当作 Release 资产安装。预期文件名不是附件存在的证据。

## 显式接入宿主

宿主接入会改写用户或 workspace 配置，必须先 dry-run。

```bash
# ZCode 预览
stinky-cobbler entry install-host --dry-run --json
stinky-cobbler entry install-host --mcp --dry-run --json

# Codex 预览
stinky-cobbler entry install-host --host codex --mcp --dry-run --json
```

只有用户确认精确目标后才执行相应的非 dry-run 命令。随后必须重启/重载宿主并跑[发布前宿主验证清单](./发布前宿主验证清单.md)。`mcpConfigured=true` 仅说明配置被检测到，不证明宿主已加载或调用成功。

`install-host` 通过目标旁的 managed sidecar 和精确 SHA-256 判断能否安全升级；当前实现只对 sidecar 匹配或内置的 2.0.0 精确模板 hash 自动升级。用户编辑返回 `conflict` 并保留。升级前创建内容寻址、独占的 byte-for-byte 备份；`--rollback` 仅在当前目标和备份都匹配记录 hash、均无链接/漂移时恢复。完整条件见[兼容与迁移政策](../兼容与迁移政策.md)。

## 初始化 workspace

先预览：

```bash
stinky-cobbler init \
  --workspace-id example \
  --profile team \
  --pack software-engineering \
  --mode reviewed-workflow \
  --root /absolute/path/to/repository \
  --dry-run
```

用户确认后去掉 `--dry-run`。初始化创建本地 `.stinky-cobbler/` 控制面和配置模板，但**不会授予读取或写入权限**。

## 权限链

一次受控操作至少要满足：

```text
persisted Task
-> TaskAuthority state/risk/scope/writeSet
-> precise delegate-capability Approval（repository-write 或 L2）
-> persisted Lease
-> governed operation
```

精确 capability Approval 绑定 Task authority hash、capability、精确根 scope、budget/expiry、policy、requester/decider 与 nonce。父 Lease 只能收窄，不能扩 scope、改 capability、超预算或跨 host session。

直接签发 Lease 前，宿主 Skill 应让用户选择时长。但 CLI 也支持配置默认值，`issuedBy` 文字标签本身不是人类确认的证据；真正可执行的边界是 Approval budget/expiry、持久化 Lease 与使用时重验。

MCP 只提交 Lease ID，服务端重读权威 Lease。不要手写 Lease JSON，也不要在拒绝后扩大 scope 重试。

## 单目标受控变更

每个 WriteIntent 只有一个目标：

1. 展示精确文件、`create|modify|delete` 与用途；
2. 在 intent 创建时捕获 `expectedPreimageHash`（create 目标不存在时为 `null`）；
3. 非 auto-allow 路径使用一次性精确 `write-confirm` Approval，绑定 intent hash/版本/目标/preimage，可选绑定 proposed content hash；
4. apply 前重读 TaskAuthority、Lease、active plan/run/subtask、路径与 preimage；
5. preimage 漂移就停止，重新创建 intent/Approval；
6. 目标成功后再记录 Evidence、ledger 和 `APPLIED`。

create/modify 的 `--auto-allow` 只跳过 write-confirm；它不会跳过 TaskAuthority capability Approval、Lease/writeSet、intent hash、路径或 preimage。delete 永不 auto-allow。

业务文件变更、Evidence、ledger 和最终状态不是一个事务。崩溃可能留下“文件已改、控制面记录不完整”，此时要诊断，不得宣称原子成功。

回滚仅在单目标 `APPLIED` journal 完整且无第三方/策略冲突时成立：create 删除本次新建文件；modify/delete 恢复独占备份。多个 intent 不构成 all-or-nothing 事务。

`write rollback` 会先持久化 `RECOVERY_REQUIRED` rollback journal，再改业务文件。若回滚被中断，先检查 intent、journal、目标与备份 hash，再运行：

```bash
stinky-cobbler write rollback-recover <write-intent-id> \
  --root /absolute/path/to/repository --json
```

该命令是幂等的 fenced recovery：仅当目标匹配 journal 的回滚前或已恢复状态时继续；第三方 bytes、备份/策略漂移或 journal 不完整都会拒绝，不能强制覆盖。

## 只读 Runtime 的取消与超时

公开 Runtime 只有 `scripted-readonly`，工具为 repository-read/list。

- cancel/deadline 使用同进程 `AbortSignal`、单调计时与边界检查；
- `CANCEL_REQUESTED` 不是最终状态，需要查询 persisted Run；
- 这是协作式取消，不是 Codex/ZCode Agent、线程或进程硬中断；
- 在途 Promise 可能继续；若停止与调用竞争，底层结果标为 `UNKNOWN`；
- persisted terminal Run 会阻止旧 owner 覆盖最终状态。

每次成功只读调用会在 owner/epoch fence 下把 tool call、Evidence 引用和预算进度 checkpoint 回 Run，以缩小进程中断后的丢失窗口；这仍不是 Evidence、Run、Receipt、ledger 的单一事务。创建 Run 时会对完整 Capsule、executor 和有序请求计算 `executionRequestHash`，终态重试、Receipt 与 finalization 必须保持同一绑定；Capsule 的 `policyVersion` 也必须等于权威持久化 Lease。缺少该 hash 的旧记录只可读取，不能按当前成功路径重试或收尾。终态还必须经过 `PREPARED → COMMITTED` finalization journal，把 authoritative terminal Run、唯一 Receipt 和精确 ledger effect 绑定起来。`runtime reconcile <runId>` 只读检查；只有 `--repair` 才会重放可确定的 `PREPARED` 尾部。journal 缺失、损坏或与 Run/Receipt 不匹配时 fail-closed，不能补写成成功。`runtime recover <runId>` 只处理 stale `RUNNING` owner，不能替代 finalization reconcile。

编排取消另有持久化 fence，会撤销相关活动 Lease、拒绝未应用 intent 并阻止后续受控 mutation，但不会撤销已落盘文件或终止宿主 worker。

人工升级使用单独的 `PREPARED → COMMITTED` 事务，精确绑定 generation、规范化 reason、Run 前后状态与 audit。若取消 fence 已开始且升级目标尚未发布，resume、escalate 与通用 reconcile 都会拒绝越过 fence；取消重试会把该事务标为 `ABORTED`。

## 编排与记忆

`orchestration` 命令组保存 contract/run/subtask/review/budget/artifact 状态。它本身不创建 Codex/ZCode worker，因此不要声称自动多 Agent 或宿主级失败隔离。

Contract 创建时会把 Profile 解析为不可变 `reviewPolicy`：`individual=SELF_REVIEW_AUDITED`，允许同源 review 但记录 `sameSourceReview` / `SELF_REVIEW_NON_INDEPENDENT`；`team` / `organization` / `regulated` / 缺失配置=`INDEPENDENT_REQUIRED`，同源 review 被拒绝。legacy Contract 未带该字段也按严格规则处理。该门禁不证明 reviewer 的现实身份或进程隔离。

当前实现只有引擎实际重读并 hash 的 `kind=file` 产物可以成为 `VERIFIED`。`kind=summary` / `kind=evidence` 被拒绝。CAS、结构化 Context/Memory、摘要检索、冲突消解和跨会话记忆不是当前功能。

### 防陈旧重放协议

调用方必须先读取当前持久化状态，不得猜测 generation：

```bash
stinky-cobbler orchestration run status <run-id> --root <workspace-root> --json
stinky-cobbler orchestration subtask show <subtask-id> --root <workspace-root> --json

# inactive subtask：使用刚读取的 retriesUsed；返回 activeAttempt
stinky-cobbler orchestration subtask dispatch \
  --run <run-id> --subtask <subtask-id> --agent <agent-id> \
  --attempt <retriesUsed> --root <workspace-root> --json

# begin、artifact report、review record 全程传回同一个 activeAttempt
stinky-cobbler orchestration subtask begin \
  --run <run-id> --subtask <subtask-id> --attempt <activeAttempt> \
  --root <workspace-root> --json

# ESCALATED Run：generation = 当前 resumeGeneration + 1
stinky-cobbler orchestration run resume <run-id> \
  --generation <next-resume-generation> --root <workspace-root> --json
```

旧 attempt 或旧 resume generation 必须被拒绝；不要在拒绝后自动递增重试，应重新读取状态并确认这是同一个人工决定。终态 Run 的同一份 create 请求只返回原 Run；确需新一代 Run 时必须显式绑定唯一终态前驱：

```bash
stinky-cobbler orchestration run create \
  --contract <contract-id> --supersedes-run <terminal-run-id> \
  --root <workspace-root> --json
```

## 从 2.0.0 迁移 authority 记录

2.0.0 Lease、Contract 和 Plan 保持可读，但不能用于新执行。它们分别可通过公共 CLI `lease revoke`、`orchestration contract cancel`、`plan cancel` 安全终止；不得手工改 JSON 冒充取消：

```bash
npx stinky-cobbler orchestration contract cancel <contract-id> --root <workspace-root>
```

- Lease 返回 `LEASE_REISSUE_REQUIRED`，需按当前 TaskAuthority/Approval 重发；
- Contract 返回 `CONTRACT_REISSUE_REQUIRED`，可先通过 CLI 取消旧记录，再新建并快照当前 `reviewPolicy`；
- Plan 返回 `PLAN_REISSUE_REQUIRED`，需重新生成、确认。

不要手工补旧 JSON 字段或改状态绕过。详见[兼容与迁移政策](../兼容与迁移政策.md)。

## 日常输出

受控请求应返回：

```text
结果：FACT / DECISION / PROPOSAL / UNKNOWN
证据：当前 CLI/MCP 输出或 file/hash
边界：未验证、未授权、未完成的事项
下一步：一个明确动作
```

遇到策略拒绝时，修正真实前置条件；不要切换到未受控工具伪装成功。
