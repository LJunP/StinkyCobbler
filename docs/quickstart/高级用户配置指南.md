# 高级用户配置指南

**本文描述当前实现，不代表任一版本已经 npm/GitHub 发布或已通过 Codex/ZCode 真实宿主验证。** 发布版本、tag/Release/资产与宿主证据必须实时核验。当前 `package.json` 要求 Node.js **>=22**。本工具为本地仓库提供只读与 L1 单目标变更门禁；分层配置见 [分层配置指南](./分层配置指南.md)，日常使用见 [使用说明书](./使用说明书.md)。

> **Cooperative Mode**：Stinky Cobbler 只治理经自身 CLI/MCP 路由的操作，不是 OS 沙箱。宿主原生文件/Shell/Git 工具及第三方 MCP 可绕过 Lease、Evidence、rollback 和 ledger。若要完整中介，必须在宿主侧隔离 worker，只暴露本工具的受控能力；该隔离不由当前仓库提供或验证。“本地”也不证明宿主/模型/插件离线。

## 安装与本地验证

公开包安装（先以 registry 实际版本为准）：

```bash
npm view stinky-cobbler version
npm install -g stinky-cobbler
stinky-cobbler --help
stinky-cobbler doctor --json
```

源码开发：

```bash
npm install
npm run build
node dist/cli.js doctor --json
npm run test:integration
npm run test:package
```

`test:package` 在临时目录安装本地 tarball，验证 CLI 和 MCP；不会发布包。

## 统一入口与宿主集成

安装后，用户可以在 AI 对话中通过 `/stinky-cobbler <request> [via=skill|mcp|auto]` 使用。宿主发现该命令需要把随包的命令文件安装到宿主目录；这个动作**不会自动执行**，需要显式运行一次：

```bash
# 预览（不写任何文件）
stinky-cobbler entry install-host --dry-run --json

# 确认后安装命令文件（默认 user 作用域：~/.zcode/commands/）
stinky-cobbler entry install-host --json

# 同时注册本地 MCP server（需要用户明确指定 --mcp）
stinky-cobbler entry install-host --mcp --dry-run --json
stinky-cobbler entry install-host --mcp --json
```

安装规则：

- `install-host` 对 command/Skill 使用目标旁的 `.stinky-cobbler-managed.json` sidecar；只有 sidecar 当前 hash 或实现内置的 2.0.0 精确模板 SHA-256 与现有 bytes 一致时才自动升级。
- 版本文字不是受管依据；检测到用户编辑、未知旧版或 MCP server 被其它 command 占用时返回 `conflict`，不覆盖、不静默合并。
- 替换前会在同目录创建 `<文件名>.stinky-cobbler-backup-<sha256>.bak` 内容寻址独占备份；MCP config 只合并 `stinky-cobbler-local` server、保留无关字段，并备份完整旧配置。
- `--rollback` 只有在 sidecar、当前 installed hash、普通非 symlink 备份和备份 hash 全部匹配时恢复；安装后用户改动、目标/备份缺失或漂移会 fail-closed。安装时使用 `--mcp`，回滚时也必须显式带 `--mcp`。
- 安装包没有 `postinstall`，`npm install` 不会修改任何宿主 `.zcode/`。

完整的 managed upgrade、已知 2.0.0 hash 和 rollback 条件见[兼容与迁移政策](../兼容与迁移政策.md)。

只读事实检查（入口决策依据，不创建 workspace、不写文件）：

```bash
stinky-cobbler entry preflight --workspace /absolute/path/to/workspace --via mcp --json
```

返回 `viaValid`、`workspaceInitialized`、`mcpConfigured` 与 `decision`（`skill-only` / `mcp-available` / `mcp-missing` / `workspace-uninitialized` / `invalid-via`）。

`via` 语义：

| via | 行为 |
|---|---|
| `skill` | 只用 Skill；不启动、不调用 MCP |
| `mcp` | 经宿主 MCP client 调用 `stinky-cobbler-mcp`；未配置时明确提示，不静默回退 |
| `auto` | 仅当需要读本地文件/仓库/控制面状态时才走 MCP |

未显式提供 `via` 时，宿主 Skill 必须展示三种模式并等待用户选择，不得静默采用 `auto`。

单独打印 MCP 注册模板：`stinky-cobbler entry mcp-config --json`。

## 唯一 Workspace Config

唯一受支持的机器配置是：

```text
.stinky-cobbler/workspace.json
```

不支持 `.stinky-cobbler/config.yaml`。配置不能存 Token、API key 或密钥。

```bash
stinky-cobbler init \
  --workspace-id example-workspace \
  --profile team \
  --pack software-engineering \
  --mode reviewed-workflow \
  --root /absolute/path/to/workspace \
  --dry-run
```

检查预览确认无误后才移除 `--dry-run`。`init` 不会覆盖既有配置；初始化账本事件为 `workspace-initialized`。选择多个 Pack 时可重复 `--pack`，但每个 Pack 必须已由 Profile 启用且不能重复。

```bash
stinky-cobbler config show --root /absolute/path/to/workspace --json
stinky-cobbler config validate --root /absolute/path/to/workspace --json
stinky-cobbler config doctor --root /absolute/path/to/workspace --json
stinky-cobbler config migrate --root /absolute/path/to/workspace --dry-run --json
stinky-cobbler config migrate --root /absolute/path/to/workspace --json
```

v2 配置通过 `plugins` 记录显式选择。Pack 推荐不会自动启用：缺省为 `unset`，`enabled: false` 为 `disabled`，只有已发现且有受信任实现的 executable Plugin 才能设置 `enabled: true`。例如：

```json
{
  "version": 2,
  "plugins": {
    "repository-read": { "enabled": true },
    "git-read": { "enabled": false }
  }
}
```

`config show/doctor` 输出 `recommendedByPacks`、`workspaceSelection`、`selected`、`effective`、`executable` 和 `implementationAvailable`；`effective` 不等于 Lease 授权。v1 只读加载不会静默迁移；先用 `config migrate --dry-run` 检查，再正式迁移。正式迁移会原子替换 config、备份到 `.stinky-cobbler/backups/` 并记录 `workspace-config-migrated`。

Stable role ID（如 `scout`、`builder`、`reviewer`）是协议字段，不可变更；`workspace.json` 仅可覆盖已知角色的 `roles.<stable-id>.displayName`。

带 `workspace` 的受控 MCP 工具要求 workspace 已完成初始化：`.stinky-cobbler/workspace.json` 必须存在、是普通文件且包含可解析 JSON。仅创建 `.stinky-cobbler` metadata 目录仍会被 MCP 以 `WORKSPACE_NOT_INITIALIZED` 拒绝；该检查发生在 Lease 校验、usage reservation 和 capability 执行之前，因此不会执行 callback 或增加 Lease usage。初始化存在后，MCP 还在同一边界做完整 config schema 与 cross-reference 校验（profile 存在、pack 被 profile 启用、plugin executable、稳定 role ID），失败返回 `WORKSPACE_CONFIG_INVALID` 并 fail-closed。配置存在不等于获得 Task、Lease、Approval 或执行授权。每次受控调用还会在 reservation 前读取持久化 Audit outbox；`prepared`、`recovery-required` 或 pending 状态读取失败都会以 `AUDIT_PERSISTENCE_FAILED` fail-closed。请使用 `audit pending` 查看并用 `audit recover` 显式恢复；MCP 不会自动恢复。旧 MCP 进程会在下一次调用边界重新读取 outbox，确认无 pending 后清除 stale 的进程内 degraded marker。

MCP 调用只引用 Lease ID；服务端在每次 admission 时重新加载工作区内的持久化 Lease，并重新执行 TaskAuthority。TaskAuthority 绑定持久化 Task 的 state/risk/scope/writeSet 等权限字段 hash；`repository-write` 与 L2 必须有精确 `delegate-capability` Approval，根授权绑定 Task hash、capability、精确 scope、budget/expiry、policy、requester/decider 与 nonce；父 Lease 只能收窄 capability/scope/budget/session。调用者提供的可变字段不构成授权。Skill 要求直接流程先询问 Lease 时长，但 CLI 本身也接受配置默认值，`issuedBy` 标签不等于人类交互证明。

Role 不是显示标签。Lease 签发时和每次具体 operation 使用时都会读取 canonical role→tools 映射；未知角色、缺失映射、不允许的 operation、capability/operation 不一致都会 fail-closed。内部 `worker` 不是通用例外，只允许 orchestration-derived 且绑定 exact subtask/attempt 的 Lease。

## Durability 基础

`.stinky-cobbler` 控制面使用 workspace-wide 跨进程锁和耐久元数据写入：可变 JSON/JSONL 的读改写在同一 workspace 锁内完成，临时文件、fsync、rename 和目录同步用于避免半个 JSON；ledger append 在返回前同步文件。当前实现不自动回收任何已存在的 workspace lock：合法但已失活/过期的 owner、缺失 owner 与损坏 owner 都会在 `waitMs` 后返回 `WORKSPACE_LOCK_BUSY`；`staleMs` 仅为兼容参数，不触发回收。残留锁必须在人工独立确认没有活跃持有者后显式诊断处理。lock owner 的 `heartbeatAt` 只作诊断元数据，不是周期性心跳或自动回收信号；RUNNING Run 则有独立的周期 `heartbeatAt`（请求边界约每 30 秒写一次存活声明，stale 判定基准为 `heartbeatAt ?? startedAt ?? createdAt`，心跳新鲜时 `runtime recover` 拒绝）。Run 心跳是尽力而为的存活声明，写入失败不影响请求执行，也不是存活证明、分布式 fencing、签名、可信时间或外部见证。

这不是数据库事务或分布式锁。Receipt、Audit outbox、Run 和 ledger 的多文件步骤仍可能留下需要显式恢复的中间状态；`audit recover` 和 `runtime recover` 不自动批准、签发 Lease、修改业务文件或推进 Task 到 `DONE`。每个 WriteIntent 只允许一个目标，并在目标成功落盘后才标记 APPLIED；自动回滚还要求 journal 完整且目标未发生第三方冲突（create 删除本次新建文件，modify/delete 恢复操作前备份）；多个 intent 之间没有全局事务。`runtime show` 会报告 Run 是否超过默认 stale 阈值，只有显式 `runtime recover <runId>` 才会把过期的 `RUNNING` Run 标记为 `FAILED`/`RUNTIME_STALE_RECOVERY`，绝不伪造成功 Receipt。`runtime reconcile` 检查终态 Run/Receipt/finalization；`--repair` 只重放可确定的 `PREPARED` 尾部，不能修复缺失、损坏或冲突 journal。两类 recover/reconcile 不可互换。SHA-256 ledger 仍不是签名、身份认证、可信时间或外部见证，非法尾部不会被自动截断或重写。
## Approval：普通 preflight 与精确能力授权

Approval 请求和决定都必须由显式 CLI 调用完成，不会由 Runtime、Receipt 或审计恢复自动生成/批准：

## 只读 Runtime

```bash
stinky-cobbler approval request --file approval-request.json --root /absolute/path/to/workspace --json
stinky-cobbler approval list --root /absolute/path/to/workspace --json
stinky-cobbler approval decide approval-id --status approved --decided-by human-reviewer --reason "明确审核意见" --root /absolute/path/to/workspace --json
stinky-cobbler approval inspect approval-id --root /absolute/path/to/workspace --json
stinky-cobbler task approval-preflight task-id --action review-output --scope report --root /absolute/path/to/workspace --json
```

普通 Approval 可以只描述 `taskId`、`action`、可选 `scope` 和 `reason`；它只满足相应 preflight，不签发 Lease、不授权写入，也不推进 `DONE`。精确 Approval 还必须完整绑定 subject/capability/scope/budget/policy/requester/expiry/nonce 等字段。写 capability 使用 `delegate-capability`；非 auto-allow 写入另需一次性消费的 `write-confirm`，绑定 WriteIntent hash、版本、精确目标和 `expectedPreimageHash`，并可绑定 proposed content hash。create/modify auto-allow 只省略后者，不能省略 TaskAuthority capability Approval。L3 始终拒绝；rejected、expired、revoked、已消费或绑定不匹配的记录不会通过对应门禁。



```bash
stinky-cobbler runtime validate \
  --task task.json --capsule capsule.json --lease lease.json \
  --root /absolute/path/to/workspace --json

stinky-cobbler runtime run \
  --task task.json --capsule capsule.json --lease lease.json \
  --script requests.json --executor scripted-readonly \
  --root /absolute/path/to/workspace --json

stinky-cobbler runtime show run-001 --root /absolute/path/to/workspace --json
stinky-cobbler runtime reconcile run-001 --root /absolute/path/to/workspace --json
stinky-cobbler runtime reconcile run-001 --repair --root /absolute/path/to/workspace --json
stinky-cobbler runtime cancel run-001 --root /absolute/path/to/workspace --json
```

Admission 强制：

1. Task 必须已持久化，状态为 `SCOPED` 或 `DESIGNED`；
2. Task、Capsule、Lease 的 workspace/task/role/lease/agent 绑定一致；
3. Role 不可写；Lease 为 active L0，且 Lease 与 Capsule 的 `writeSet` 都是空数组；
4. Capsule 仅可请求 `repository-read`、`repository-list`；
5. scope/readScope 不能访问 `.stinky-cobbler` 或敏感路径；
6. Capsule/Lease 未过期，预算合法，Lease capability 覆盖请求。

每个请求通过 Broker 执行，并产生 Tool Call、证据 hash/locator 和 Receipt。Runtime 不修改 Task state、不写业务文件、不执行 test、shell、网络、Git 写入或 `docs-index.build`。Run `COMPLETED` 不是 Task 完成、验收或审批。Broker 级失败 fail-closed：不支持或未授权请求为 `RUNTIME_TOOL_NOT_ALLOWED`，工具、路径、文件系统、scope 或读取失败归一化为 `RUNTIME_TOOL_FAILED`，Evidence 记录或校验失败（包括 owner fence 失效）归一化为 `RUNTIME_EVIDENCE_PERSISTENCE_FAILED`；这些结果会阻断 Tool Call，并由 Supervisor 传递为阻断 Run。

Runtime Supervisor 集中执行 `maxTurns`、`maxToolCalls`、`maxFiles`、`maxBytes`、`maxOutputBytes` 和 monotonic `maxMinutes`。tool attempt（包括 blocked/failed）计入 toolCalls；唯一规范化普通文件计入 files；重复文件不重复计数但 bytes 仍累计；输出按 UTF-8 bytes 计量。预算超限使用 `RUNTIME_BUDGET_EXCEEDED`，deadline 使用 `RUNTIME_DEADLINE_EXCEEDED`。Runtime Run 的 ownerToken/fenceEpoch 只提供 workspace-local cooperative fence；cancel/recovery 后旧执行路径不能继续写控制面，但不保证硬中断，也不是身份认证或 distributed lock。`runtime cancel` 持久化取消并在同进程通过 AbortSignal cooperative 取消；非合作 I/O 不保证硬中断，跨 CLI 进程仅能在请求边界观察。

每次成功 read 会在相同 owner/epoch fence 下 checkpoint toolCalls、EvidenceRefs 与预算进度，缩小 crash 丢失窗口。终态仍必须通过 `PREPARED→COMMITTED` finalization journal 绑定 authoritative Run、唯一 Receipt 和精确 audit effect；这不是 Evidence/Run/Receipt/ledger 单一事务。

## Persistent Evidence References

成功的只读 Runtime Tool Call 会将 EvidenceRef metadata 持久化到 `.stinky-cobbler/evidence/`，可用以下只读命令查询：

```bash
stinky-cobbler evidence list --root /absolute/path/to/workspace --json
stinky-cobbler evidence show evidence-<id> --root /absolute/path/to/workspace --json
stinky-cobbler evidence inspect evidence-<id> --root /absolute/path/to/workspace --json
```

只保存 metadata，不保存源文件正文或任意工具输出原文。当前 hash 是序列化 tool-output envelope 的 SHA-256，不是 raw bytes 证明、签名、可信时间或外部见证。Evidence persistence 不启用 Evidence Gate，不自动通过 Approval，不授权业务写入，不修改 Task 或推进 `DONE`；持久化失败必须如实阻断 Runtime。Runtime Evidence 的 owner check、幂等检查、Evidence JSON 写入和 `evidence-recorded` Ledger append 在同一个 workspace lock 临界区内完成，只关闭 owner 失效后才开始写入的 TOCTOU；它不是 Evidence、Run、Receipt、Ledger 多文件事务。若 Evidence 先提交、cancel/recovery 后获锁，orphan Evidence 仍可能出现，诊断只报告、不自动删除。`evidence list --orphan` 和 `evidence inspect` 的 orphan/linkage 结果只描述控制面引用关系，不证明原始源内容。

`runtime diagnose [runId] --root /absolute/path/to/workspace --json` 提供只读的 Run/Ledger/Receipt 生命周期诊断。它报告缺失关联、孤儿引用、语义冲突、损坏和 `UNVERIFIABLE` 状态，不创建 workspace lock，不追加或重写 Ledger，不创建/删除 Receipt，也不执行 `runtime recover` 或 `--repair`。报告是非原子读取的当前观察结果；`INDETERMINATE` 不是安全通过、授权或历史真实性证明。


ZCode 用户级配置写入 `~/.zcode/cli/config.json`；workspace 级配置写入 `<repo>/.zcode/config.json`。不要放置密钥或使用动态下载：

```json
{
  "mcp": {
    "servers": {
      "stinky-cobbler-local": {
        "command": "stinky-cobbler-mcp",
        "args": []
      }
    }
  }
}
```

固定注册 10 个工具：`validate_contract`、`resolve_config`、`recommend_task`、`evaluate_lease`、`repo_read`、`repo_list`、`repo_write`、`repo_delete`、`git_read`、`docs_index`。`repo_write`/`repo_delete` 只处理已确认的单目标 intent；`docs_index build` 需要专用 L1 Lease 并只写 `.stinky-cobbler/docs-index.json`；它不是 Runtime 的只读工具。`test-run` 不注册，客户端不可调用。

## 审计边界

`ledger.jsonl` 是本地 SHA-256 hash-chain，只记录经 Stinky Cobbler 路由的控制面事件。`ledger verify` 仅验证当前读取链的 JSON、字段、前序链接与 hash 是否自洽，不能发现宿主或第三方工具绕过本控制面的操作。Runtime Run 的 `run-created`、`run-transitioned`、`run-recovered` 事件包含安全的 `runId`/状态字段，便于观察生命周期；它们不构成授权、重新执行或 `DONE` 事实，且 Run JSON 与 ledger 写入仍不是原子事务。它不是不可篡改存储、数字签名、可信时间、外部见证或身份认证；当前 append 已在 workspace-wide lock 内执行并 fsync，不能替代上述保证。非法 JSON/空行/残缺尾部只报告错误，不自动截断或重写。

`audit pending/recover` 只处理固定的控制面审计恢复，不改业务文件、Receipt 正文或历史账本，也没有 `--force`。审计写入失败必须如实报告，不得宣称调用已记录或继续高风险动作。

## 编排、审查与记忆边界

Contract 创建时会把 Profile 解析为不可变 `reviewPolicy`：`individual=SELF_REVIEW_AUDITED`；`team` / `organization` / `regulated` / 缺失配置=`INDEPENDENT_REQUIRED`。legacy Contract 缺字段也默认严格。前者允许同源 review 但保留 `sameSourceReview` / `SELF_REVIEW_NON_INDEPENDENT`；后者拒绝同源 review。修改 Profile 不会改写既有 Contract，采用新策略必须新建 Contract。

调用方必须用持久化 generation 防陈旧重放：先用 `orchestration subtask show` 读取 `retriesUsed` 并作为 dispatch `--attempt`；begin/artifact/review 继续传 dispatch 返回的同一个 `activeAttempt`。ESCALATED Run 先读 `run status`，resume 传当前 `resumeGeneration + 1`。旧 token 被拒绝后必须重读状态，禁止盲目递增。终态 Run 的 exact create retry 返回原 Run；新一代必须用 `--supersedes-run` 绑定唯一终态前驱。详见[使用说明书](./使用说明书.md#防陈旧重放协议)。

当前实现只有 `orchestration artifact report --kind file` 可以产生 VERIFIED 产物：引擎读取工作区内真实文件、计算内容 hash，并在后续 dispatch 时重新核对引用。`kind=summary` 与 `kind=evidence` 必须拒绝，不能生成 synthetic hash、不能进入 `inputArtifacts`，也不能被描述为可靠的跨轮上下文、Evidence 或长期记忆。当前子任务上下文由契约锚点 `contractGoal` / `globalAcceptanceCriteria`、子任务 `goal`、`domainInstructions` 和显式引用的已验证文件产物（含 `path` + `contentHash`）组成；结构化摘要、压缩、检索、冲突消解、过期/撤销与长期记忆治理不属于当前实现。

2.0.0 Lease/Contract/Plan 可读但因缺少当前 authority 快照不可执行，必须重发 Lease、新建 Contract、重新生成/确认 Plan。它们分别有公共 CLI `lease revoke`、`orchestration contract cancel`、`plan cancel` 安全终止路径；参见[兼容与迁移政策](../兼容与迁移政策.md)。

## 分层配置（2.0 增强，初始化后使用默认值）

内置默认值减少初始化后的参数填写，但安装、宿主接入、workspace 初始化、Task/Approval/Lease 与真实宿主验证仍不可省略。高级用户按需覆盖，详见独立文档
[`docs/quickstart/分层配置指南.md`](./分层配置指南.md)。核心要点：

- **两层**：内置默认（包内 `policies/*.yaml`，勿改，会被更新覆盖）+ 用户覆盖（`.stinky-cobbler/policies/*.yaml`，优先，可 git 审计）
- **可自定义**：编排预算/规模上限/Lease 默认/写入大小、专才注册表（追加+覆盖+自定义名称）、审查自动否决阈值、话术/审查风格模板、契约模板库、敏感路径追加（只增不减）
- **安全底线锁定**：内置敏感路径不可删、仓库文件 delete 不 auto-allow、L3 在当前版本始终拒绝且不能由确认解锁、审计不可关、收敛阈值只可收紧、`general` 专才回退不可消失
- **只读查看**：`orchestration config show` / `specialist list` / `template list`
- **Ledger 归档**：`ledger archive --before-days N` 后 `ledger verify` 仍跨归档可校验
