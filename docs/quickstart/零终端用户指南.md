# 无终端操作者指南

> 文件名保留兼容旧链接，但 Stinky Cobbler **不是零配置或无人值守产品**。无终端用户仍需要一位可信安装者完成受支持 Node.js、安装、宿主配置、workspace 初始化与真实宿主验证。

公开 npm 版本、GitHub tag/Release/资产与 Codex/ZCode 验证状态会变化，必须由安装者实时核验；源码版本或配置检测不能替代。

## 你可以要求安装者做什么

1. 先核验 registry/Release 的实际版本；验证 checkout 时固定并记录当前源码 bytes。
2. 对宿主配置先运行 `entry install-host --dry-run` 并展示精确改动。
3. 由你确认后安装，再重启/重载 Codex 或 ZCode。
4. 在一个专用测试仓库初始化 workspace，并完成真实宿主读/写/删除/取消验证。
5. 把结果按 FACT / UNKNOWN 报告，不把 `mcpConfigured=true` 当成实际调用成功。

## 你在批准什么

Stinky Cobbler 的核心是本地仓库权限与变更门禁：

- Task 说明目标、范围、writeSet 与风险；
- 精确 Approval 绑定 Task hash、capability、scope、budget/expiry 和批准者元数据；
- Lease 是限时、限 scope、限调用次数的本地 bearer capability；
- 每次写入只有一个文件目标，并绑定写前 `expectedPreimageHash`；
- delete 永不 auto-allow；create/modify auto-allow 也不会跳过 TaskAuthority Approval、Lease 或 preimage。

安装、初始化、测试或账本通过都不是写入授权。

## 你必须知道的限制

- Cooperative Mode 只约束经 Stinky Cobbler CLI/MCP 的操作。宿主原生文件工具、Shell、Git 或第三方 MCP 可绕过。
- 它不自动完成多 Agent 工作；编排只是本地 contract/run/subtask/review 状态。
- 它不保证 reviewer 的现实身份或宿主隔离。Contract 创建时 `individual=SELF_REVIEW_AUDITED`；`team` / `organization` / `regulated` / 缺失配置=`INDEPENDENT_REQUIRED`，同源 review 被拒绝。
- “本地”不代表 Codex/ZCode、模型或插件离线。
- 当前实现没有 CAS 或长期 Context/Memory；`summary/evidence` 不能成为 VERIFIED 产物。
- Runtime 取消/超时是协作式的，不是宿主 Agent 或进程硬中断；在途结果可能为 UNKNOWN。
- 多个 WriteIntent 不是一个跨文件事务。崩溃可能留下需人工诊断的不完整记录。

## 你应看到的回复

```text
结果：FACT / DECISION / PROPOSAL / UNKNOWN
证据：具体命令、记录、文件和 hash
边界：哪些事情还没有验证或授权
下一步：一个明确动作
```

任何“自动安装并完成”“所有数据绝不出本机”“自动多 Agent 全程执行”“失败自动隔离”“现实身份和隔离已保证”的说法，都不是当前可验证事实。
