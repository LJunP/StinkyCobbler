# Changelog

## 1.0.0

- First formal release (1.0.0): ZCode + Codex dual-host support, 236 tests, all real-host verification complete.
- Added persisted EvidenceRef metadata records with read-only `evidence list/show/inspect` commands.
- Added explicit Approval request/decision records and read-only approval preflight.
- Added workspace-wide locking, durable control-plane JSON writes, ledger verification, stale Runtime recovery, and package/runtime integration checks.
- Added security and release-boundary documentation.
- Added the `/stinky-cobbler` unified entry with `via=skill|mcp|auto` routing, read-only `entry preflight`, and explicit `entry install-host` host integration.
- Runtime admission now requires the persisted workspace Task (`RUNTIME_TASK_NOT_PERSISTED` / `RUNTIME_TASK_AUTHORITY_MISMATCH`) and MCP performs a full workspace-config admission (`WORKSPACE_CONFIG_INVALID`).
- Approval records support an optional `expiresAt` with assessment-time expiry; RUNNING Agent Runs carry a best-effort periodic `heartbeatAt` for stale recovery.
- Added a release tag/version gate (`scripts/release-gate.mjs`): git tags must equal `v${packageJson.version}` and workflow_dispatch runs must declare a matching version; `release-contract` tests no longer hardcode a version.
- Pinned CI and release-candidate GitHub Actions to immutable commit SHAs (`actions/checkout` and `actions/setup-node` at v4.4.0) instead of mutable `@v4` tags.
- Added release SBOM generation (`scripts/generate-sbom.mjs`, CycloneDX 1.5 over the full lockfile dependency tree with SHA-512 integrity hashes) and tarball checksum generation (`scripts/generate-checksum.mjs`, sha256sum format), both verified in the release-candidate workflow.
- The release-candidate workflow uploads the tarball, its checksum, and the SBOM as a GitHub Actions artifact (pinned to `actions/upload-artifact` at v4.6.2), so release artifacts can be downloaded and independently verified.
- Added an independent read-only security review with a pre-release checklist (`docs/security/发布前安全审查清单.md`), including verified findings: a `git show` revision argument bug, sensitive-name gaps, and remaining architecture-level limits.
- Fixed P1 findings: `git show <revision>` now places the `--` terminator after the revision so the revision is honored; `git_read` fails closed unless the workspace itself is the git repository top level (blocking nested/non-repository workspaces) and no longer inherits `GIT_DIR`/`GIT_WORK_TREE`/`GIT_INDEX_FILE`; the sensitive-path list now covers `.npmrc`, `netrc`, `keyring`, `*.tfstate`, `auth.json`, `.envrc`, and `.pypirc`.
- Added user-confirmed lease issuance (`lease issue/show/list/revoke`): read-only L0 capability leases (repository-read/git-read/docs-index) are generated, persisted under `.stinky-cobbler/leases/`, and audited via `lease-issued`/`lease-revoked` ledger events; issuance is never automatic, honors task persistence, and validates capability allowlist, read scopes, call limits (1-100), and expiry (1-1440 minutes).
- Added the orchestration plan model (`plan create/show/list/confirm/cancel`): structured plans with role steps, tools, read scopes, and write-intent placeholders (always empty until L1), generated rule-driven from the persisted task (reusing the role recommender), persisted under `.stinky-cobbler/plans/`, confirmed only via a matching approved `plan-confirm` Approval, and audited via `plan-created`/`plan-approved`/`plan-cancelled` ledger events. Execution of plans arrives with the scheduler batch.
- Added the scheduling loop (`plan execute/step/step-done/step-fail/finish/fail`): an APPROVED plan moves to EXECUTING; each step transitions PENDING→RUNNING→COMPLETED/FAILED, the scheduler issues one controlled lease per mapped step capability (`repository-read`/`git-read`/`docs-index`, agent defaults to `host-agent`), and the host AI session performs the actual work with those leases. Step/plan completion and failure are audited via `plan-executing`/`plan-step-completed`/`plan-step-failed`/`plan-completed`/`plan-failed` ledger events.
- Added the role→tools mapping as a config file (`policies/role-tools.yaml`): all 12 built-in roles now map to their default read-only tools (scout/planner/architect/builder/testwright/sentinel/reliability/reviewer/verifier/operator/scribe/conductor), validated at registry load (`ROLE_TOOLS_UNKNOWN_ROLE`/`ROLE_TOOLS_UNKNOWN_TOOL`/`ROLE_TOOLS_DUPLICATE` fail closed); new roles can be added without code changes. Writer capabilities remain pending the L1 write batch.
- Added step result passing: `plan step-done --evidence <ref>` records the step's reported result references (1-20 unique non-empty strings up to 256 chars, `PLAN_STEP_EVIDENCE_INVALID` fail closed) on the completed step, and later steps read them via `plan show`. References are host-reported facts with no automatic linking or existence checks.
- Added the controlled write authorization model (L1): `plan write-request` proposes write intents (1-20 targets; control-plane, sensitive, `.git`, and executable/binary targets fail closed via the shared path policy), users confirm a subset through `approval request` (action `write-confirm`, scope=selected targets) + `plan write-confirm`, and `lease issue --capability repository-write --write-set` issues L1 whitelisted write leases (`WRITE_SET_EMPTY`/`WRITE_TARGET_FORBIDDEN` fail closed). Content write execution arrives in the next sub-batch.
- Added write execution (L1): `applyWrite` (backed by `repo_write` MCP tool and `write apply` CLI) validates the write lease, the confirmed intent, target bounds, and content size; backs up the previous file under `.stinky-cobbler/backups/write-<id>/`; atomically writes the content; records `kind=file` Evidence with the content hash; appends a `write-applied` ledger event; and marks the intent APPLIED (duplicate applies fail with `WRITE_ALREADY_APPLIED`). Storage is authoritative: the intent is re-read inside the lock, so stale in-memory copies cannot bypass the APPLIED guard.
- Completed the L1 write loop: steps with pending or confirmed writes cannot complete (`PLAN_STEP_PENDING_WRITES`); `write list/show` provide audit queries; `write rollback` explicitly restores applied writes from their pre-write backups (restoration Evidence + `write-rolled-back` ledger event, intent → ROLLED_BACK, duplicate rollbacks rejected), skipping created files without a backup rather than deleting them; MCP `repo_write` is covered end-to-end through the full invocation chain.
- Applied the P2 hardening fixes: `WORKSPACE_CONFIG_INVALID` reasons are truncated to 200 chars with control characters stripped; the package-smoke forbidden-file check now covers `.env.*`, `secrets.json`, and `netrc`; SBOM purls URL-encode scoped package names (`%40`) and release verification compares components one-to-one against the lockfile; the security docs now state the cooperative-lock reentrancy constraint and that leases are not signed credentials.
- Added the crash-consistency matrix (`test/crash-matrix.test.ts`): truncated or corrupted ledgers fail closed on every appending write path and are reported by `verifyLedger` (`HASH_MISMATCH`/`PREVIOUS_HASH_MISMATCH`); diagnostics recognize corrupted runs, missing lifecycle events, status/ledger conflicts, and orphaned receipt refs; `audit recover` and `reconcile --repair` are blocked while the ledger is corrupted; a missing ledger self-heals from genesis; and an interrupted write keeps its APPLIED intent idempotent. No product-logic gaps were found.
- Added the end-to-end user path (`test/e2e-user-path.integration.test.ts`): a temporary-HOME black-box walk from `entry install-host` through init/task/lease, plan confirm/execute/step/finish, and confirmed write apply/rollback, ending with audit queries. Delivered `docs/quickstart/发布前宿主验证清单.md` for the same flow in the real host.
- 修复 MCP 注册位置（4C 真实宿主验证发现）：ZCode 用户级 MCP 配置在 `~/.zcode/cli/config.json`（`mcp.servers`），此前 install-host 误写到 `~/.zcode/config.json`（ZCode 不读取，导致已注册但宿主无工具）。现在 user scope 写 `~/.zcode/cli/config.json`，workspace scope 仍写 `<repo>/.zcode/config.json`（ZCode workspace 级位置）；MCP server 命令注册为**绝对路径**（PATH 解析，避免 ZCode GUI 不继承 shell PATH）；`preflight` 检测位置同步为 cli/config.json + legacy 位置 + `~/.agents/mcp.json`（ZCode 同 scope fallback，支持顶层 `mcpServers` key）；legacy 位置检测到时输出迁移提示（不自动删除）。
- Added controlled deletes (`applyDelete`, MCP `repo_delete`, CLI `write delete`): a confirmed delete intent backs up the target file, removes it, records file Evidence with the pre-delete content hash (`source: repository-delete`), appends a `delete-applied` ledger event, and marks the intent APPLIED. Deletes are never auto-allowed and only run through the explicit write-confirm flow; `rollbackWrite` restores deleted files from the backup with zero changes; missing targets fail with `WRITE_TARGET_MISSING`; applying a delete against a non-delete intent fails with `WRITE_ACTION_MISMATCH`. Discovered through the Codex C4 real-host test.
- Added the lease expiry grace period (`DEFAULT_GRACE_PERIOD_MINUTES = 15`): an expired lease still admits the SAME task within the grace window so an in-flight task is not interrupted; all remaining gates (call limit, writeSet, NEVER_AUTONOMOUS, L2/L3) still apply inside the grace window; beyond the window or for a new task it fails closed with `LEASE_EXPIRED`. `evaluateLease` and the runtime admission share `isLeaseExpiredBeyondGrace`.
- Added the auto-allow write path (`plan write-request --auto-allow`): regular create/modify intents are created already CONFIRMED without a write-confirm Approval (audited via a new `write-auto-allowed` ledger event; backups/Evidence/rollback unchanged). Delete intents can never be auto-allowed (`WRITE_AUTO_ALLOW_DELETE_DENIED`); sensitive/control-plane/.git/executable targets remain engine-forbidden; the L1 write lease + writeSet whitelist stays as the second line of defense; the explicit write-confirm flow is unchanged. This implements the confirmed density decision: routine writes no longer need per-write confirmation, irreversible operations still do.
- Added Codex host support (`entry install-host --host codex`): the engine and ZCode host are unchanged; Codex installs the skill into `~/.codex/skills/stinky-cobbler/SKILL.md` (no slash-command file — Codex has no custom command mechanism) and registers the MCP server into `~/.codex/config.toml` (`[mcp_servers.stinky-cobbler-local]`, absolute command path) via TOML parse/merge that preserves every existing field and server (backed up as `config.toml.bak-*`; conflict/invalid fail closed). Host abstraction lives in `src/entry/host-spec.ts` (`HostSpec` for zcode/codex); `entry preflight --host` filters MCP detection, `entry mcp-config --host codex` prints the TOML template. Dry-run previews now show only the MCP-relevant subset instead of the whole host config, so credentials in `config.toml` (e.g. `model_providers.*.experimental_bearer_token`) are never printed. New dependency: `smol-toml`.
- 新增「泛化/全量范围请求」规则（SKILL.md，安全断言测试发现）："所有文件/全部/整个项目"等泛化范围请求不得直接接受——先只读核实缩小为明确文件清单，展示并质疑范围，用户确认清单后才走受控写入流程；未确认则不执行任何写入。
- 显式退出改为**确认式**（SKILL.md）：用户说"停止使用 Stinky-Cobbler / 停止使用该工具 / 退出工具模式"等时，先弹确认选项（停止使用该工具（推荐）/ 继续使用），点击后才解除激活；确认框不计入请求弹框上限。
- 新增「会话内激活模式」（SKILL.md）：会话首次 `/stinky-cobbler` 后即激活，后续请求无需前缀；显式退出（"退出工具模式"等）才解除激活，无关请求正常回答且工具保持待命，新会话自然失效。
- 「弹框规则」推荐语义修正（SKILL.md）：推荐 = 对当前请求**最优**的方案（附用户能懂的理由），不是"最短/最省事"——省事只是点推荐的自然结果；无法确定最优时如实说明不确定性。
- 「弹框规则」收紧（SKILL.md）：一次请求弹框硬上限 2 个（via 选择 + 必要的一次写入/初始化确认）；workspace 未初始化时**只弹一次框**（方向与参数确认合并，选 1 后直接 init，不再二次确认）；参数全部代填默认值（名称=当前目录名），术语不出现在弹框。
- 新增「弹框规则」（SKILL.md）：所有用户决策弹框必须用**用户语言**（只描述做什么/结果，禁止内部术语如 workspace-id/profile/Lease/preflight 等），必须且只能标注一个（推荐）选项，点选后立即继续。workspace 未初始化时给出固定的三选项示例文案（在当前项目初始化并继续（推荐）/ 换一个已初始化的项目 / 只看流程不实际读取）。
- `/stinky-cobbler` via 交互修正（点选式）：请求未带 `via` 时，Skill 弹出**通俗文案选项**等待用户点击后才继续，绝不静默默认——「纯 Skill」→ `via=skill`、「Skill + MCP」→ `via=mcp`、「自动」→ `via=auto`，按请求类型附一个推荐（展示层与执行层解耦）；显式 `via=xxx` 参数仍然有效。`via` 是用户唯一的开始决策。
- `entry install-host` now also installs the matching skill file (`~/.zcode/skills/stinky-cobbler/SKILL.md`) that the command file references (`skills: stinky-cobbler`); without it the entry command would load with a dangling skill reference. The skill install shares the command file's semantics: preview/installed/ready/conflict, never overwriting different content, dry-run writes nothing. The `entry preflight` test that assumed the real host has no MCP config is now isolated with a temporary home.
- Real-host verification (2026-08-10, executed in this environment with the user's explicit go-ahead): global install from the local tarball, `entry install-host` (command file + skill), and MCP registration into the real `~/.zcode/` all verified; installed CLI smoke (init/ledger verify/plan list/write list/preflight) passes; preflight detects the registered MCP (`mcp-available`). `npm audit` now passes with 0 vulnerabilities against the official registry (the earlier `[NOT_IMPLEMENTED]` failure was the npmmirror mirror not implementing the audit endpoint). Release artifacts (tarball, sha256 checksum, CycloneDX SBOM, one-to-one SBOM↔lockfile verification, version gate) all verify. Publishing (`npm publish --provenance`) remains user-executed (needs npm auth/OIDC).

Known limitations remain: multi-file control-plane operations are not one database transaction; the local SHA-256 ledger is not a signature, identity proof, trusted time source, or external witness; Evidence hashes cover serialized tool-output envelopes rather than raw source bytes; and public `test-run`, `host-injected`, business-write, network, deployment, and automatic `DONE` capabilities remain unavailable.
